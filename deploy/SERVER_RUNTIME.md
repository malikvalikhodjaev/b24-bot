# Рабочий бот на VPS — v0.2.0

## Размещение

Основной запуск — пользовательская служба `fom-bitrix-bot.service` на `malik@130.49.168.29`. Код находится в `/home/malik/datfo-crm-bot`, Python — в `.venv/bin/python`; среда использует отдельный CPython 3.12, не системный Python Ubuntu. Часовой пояс — Asia/Tashkent. Служба стартует с `--sales-bot`, перезапускается после сбоя и включается при старте пользовательского systemd; для пользователя malik уже включён Linger.

Основная ветка исходников в существующем репозитории — `codex/fom-bot-server`, подкаталог `datfo-crm-bot`. Отдельная ветка `codex/fom-bot-runtime` содержит ровно дерево этого подкаталога для небольшого серверного Git-bundle. Поэтому на сервер не нужно переносить презентации и другие проекты Datfo. В манифесте выпуска указываются оба Git SHA и связь деревьев; версия приложения — 0.2.0. Никакие изменения чужих локальных файлов не входят в выпуск бота.

У репозитория закрытый доступ. Первое размещение использует Git-bundle по SSH, без передачи учётных данных GitHub на VPS. Серверный origin указывает на исходный репозиторий; дальнейший fetch по HTTPS потребует собственной авторизации, либо можно снова передать проверенный bundle по SSH.

## Закрытые данные

В Git не включаются `.env`, `registration.json`, `settings.json`, SQLite-базы, журналы, локальные резервные копии и `.venv`. В рабочем каталоге они доступны только пользователю malik. В серверной `.env` подключение Б24 задаётся прямым URL; Windows-путь BITRIX_CONFIG_PATH не переносится.

Переносятся согласованные SQLite-копии `crm_bot.sqlite3`, `simulation.sqlite3`, `communications_test.sqlite3`; основная база содержит Telegram offset, регистрации/роли, черновики, операции/этапы, заявки, напоминания и журналы доставки. Для каждой базы сравниваются таблицы, число строк и SHA256 содержимого. Переносятся также актуальная регистрация администратора и проверенная ссылка мини-приложения `data/miniapp-publication.json`. Старые пакеты от 6 октября для переключения не используются.

## Первое переключение

1. Сохранить код в Git, проверить отсутствие секретов и собрать bundle ветки runtime. Установить отдельный CPython 3.12 через проверенный uv; хеш официального архива проверяется до исполнения.
2. Передать bundle в `/home/malik/.local/share/fom-bot-deploy/incoming/fom-bot-v0.2.0.bundle`. Выполнить сохранённый `deploy/install-git-release.sh` с этим абсолютным путём. Он клонирует код, создаёт venv, запускает тесты и устанавливает только свой юнит. Бот на этом этапе не запускается.
3. Передать закрытые настройки отдельно и выполнить `.venv/bin/python run.py --sales-bot --check-online`. Это только чтение Telegram/Б24; локальный poller продолжает работу.
4. Убедиться, что нет отправляемых операций и CRM/напоминаний. Остановить единственный локальный процесс по совпадению PID, команды, интерпретатора и времени создания. Снять свежие копии всех баз SQLite через backup API, проверить целостность/содержимое и сохранить локальный rollback.
5. Установить последнее состояние на VPS, сравнить таблицы и offset, только затем выполнить `systemctl --user enable --now fom-bitrix-bot.service`. Проверить startup, background.ready, один MainPID, отсутствие Telegram 409/ошибок, сохранённый черновик и напоминания.
6. Сохранить `data/server-hosting.json` на ноутбуке. После успешного переноса этот маркер блокирует обычный локальный запуск poller; демонстрация и онлайн-проверки остаются доступны. Локальные базы сохраняются как архив, новые действия получает серверная база.

Для согласованного переноса используется `tools/migrate_state.py`: команда create снимает SQLite backup после остановки poller, команда verify сравнивает все таблицы по манифесту. `deploy/install-private-state.py` проверяет SHA256 и точный список файлов закрытого архива, требует остановленную службу, не заменяет существующие базы и устанавливает права 0600. Передавать токен, webhook и базы можно только на подтверждённый пользователем сервер; эти данные остаются вне Git.

## Работа со службой

```bash
systemctl --user status fom-bitrix-bot.service --no-pager
systemctl --user show fom-bitrix-bot.service -p MainPID -p ActiveState -p SubState -p NRestarts
journalctl --user -u fom-bitrix-bot.service -n 50 --no-pager
git -C /home/malik/datfo-crm-bot rev-parse HEAD
```

Содержимое `.env`, базы, webhook и токен не выводить в журнал или терминал. После правки кода публикуется новый Git-выпуск, проверяются тесты, переносится только код и перезапускается эта служба. Соседние дашборды, ежедневный Telegram-бот и их базы не требуют перезапуска. Поле состояния и база на VPS не заменяются старыми локальными копиями при обновлении кода.

## Обновление и откат

Для следующей версии подготовить новый bundle runtime и записать текущий SHA/резервную SQLite-копию. Проверить чистоту tracked-файлов и совместимость схемы. Остановить только `fom-bitrix-bot.service`, fetch конкретного bundle и checkout подтверждённого SHA, выполнить проверки и вновь запустить службу. `.env`, registration.json и data остаются прежними. Если проверка кода не проходит, вернуть предыдущий SHA до старта; если старт не подтверждён, остановить новый процесс и изучить журнал. Входящие Telegram-сообщения сохраняют тот же offset из рабочей базы.

Автоматический откат на ноутбук допустим только после подтверждённой остановки VPS-poller и переноса последней серверной базы. Два обработчика одного токена одновременно не запускать. Для чтения доступны `getMe` и `getWebhookInfo`; второй `getUpdates` для диагностики не использовать.

Справочник среды: [управляемый Python uv](https://docs.astral.sh/uv/guides/install-python/). Подтверждение фактического переноса, Git SHA и проверок сохраняется отдельным отчётом `qa/SERVER_RELEASE.md`; старые записи в deploy/INSTALL_VPS.md описывают подготовку 6 октября.
