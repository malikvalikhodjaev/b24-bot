# Правила работы с FOM-ботом

Применяются ко всему репозиторию `malikvalikhodjaev/b24-bot`. Зафиксированы по итогам работы и согласованы пользователем 21 октября 2026 года. Новые указания пользователя имеют приоритет; эти правила не требуют повторного согласования уже разрешённых действий.

## Перед началом задачи

- Прочитать этот файл, актуальные записи `EVOLUTION.md` и документацию затрагиваемого сценария. Для размещения читать `deploy/SERVER_RUNTIME.md`. В `README.md` есть исторические этапы: актуальность проверять по Git и последним подтверждённым записям.
- Проверить ветку, рабочее дерево и текущую реализацию. Не считать незакоммиченные локальные файлы общим состоянием проекта. Сохранять посторонние правки и сырые источники.
- Самостоятельно сформулировать короткий сценарий: роль → действие → ввод → создаваемые сущности и связи → ответственный → результат для пользователя. Сразу учесть отмену, отсутствие данных и ошибку сохранения.
- Определить несколько проверяемых критериев готовности. Для небольшой правки достаточно короткой рабочей заметки; отдельный документ и новый круг согласований не нужны. Спрашивать только о недостающей информации, которая существенно влияет на результат; доступную независимую работу продолжать.

## Контекст и согласованные решения

- Разделять менеджеров продаж ФОМ и исполнителей техподдержки. Меню, права, статистика и маршруты соответствуют роли. Названия Datfo, ФОМ и названия подразделений не доказывают одинаковые процессы.
- Проверять источник каждого справочника и поля: Б24, УТ или новая платформа. Не придумывать связи регионов, значения списков, права подключения и соответствия полей. Подтверждённые соответствия сохранять рядом с реализацией или в документации сценария.
- Сохранять согласованные варианты при последующих изменениях. В частности, сделка по названию допускается без обязательного ИНН; ИНН позволяет выбрать фирму или её аптечную точку. Замена поиска по FOM ID на поиск по ИНН не отменяет сделку по названию. Данные выбранной существующей точки использовать повторно, не заставляя вводить их заново.
- Учитывать границы интеграций: Б24 используется в действующем сценарии; переход на `office.aifom.uz` выполнять по отдельному указанию. Источник справочника и место сохранения заявки могут отличаться.
- Не удалять существующий сценарий ради упрощения другого без основания в запросе пользователя. Открытые вопросы и изменения решений фиксировать явно, исторические записи не переписывать.

## Пользовательский опыт

- Начинать с понятного действия сотрудника: создать сделку, добавить аптеку, отправить заявку, поставить напоминание. Подписи должны объяснять, что произойдёт после нажатия. Служебные команды, коды операций и внутренние идентификаторы не выводить без пользы для пользователя.
- Для связанных полей использовать единую Mini App. Пошаговые вопросы оставлять там, где ответ определяет следующий маршрут. Основные кнопки открывают нужную форму сразу; у формы одно основное действие.
- Использовать контекстные подсказки у поля, простой язык и компактное оформление. Термин «сделка» сохранять и в узбекском интерфейсе. Отдельная длинная инструкция не заменяет понятный сценарий.
- Ожидание, отмена и ошибка — часть интерфейса. Сразу показывать начало долгого действия, блокировать повторную отправку, объяснять отсутствие результата и предлагать следующий шаг. После отмены возвращать понятное меню. Неопределённый ответ CRM требует проверки сохранения, чтобы повторная попытка не создала дубль.
- До передачи пользователю самостоятельно пройти затронутый маршрут на мобильном размере: подписи, количество действий, клавиатуру, выбор даты/времени, ожидание и итоговое сообщение. Пользователю оставлять проверку бизнес-логики и удобства в реальной работе, а не первый поиск очевидных дефектов интерфейса. Если проверка недоступна, прямо обозначить, что осталось непроверенным.

## Проверки соразмерно изменению

- Для правки текста или оформления проверить затронутые экраны и языки, синтаксис при изменении кода и отсутствие случайных изменений. Не добавлять тесты, повторяющие текст реализации, и не запускать весь набор без причины.
- Для поведения проверять результат и существенные риски: создание и связи сущностей, роль и ответственного, повторное нажатие, восстановление после ошибки, распределение и напоминания. Использовать подходящие существующие тесты; добавлять новые для значимого непокрытого поведения.
- Полный прогон выполнять при изменениях общих компонентов, широком влиянии или нерешённых регрессионных рисках. После успешных проверок не повторять их без нового изменения или причины.
- Для QA использовать изолированные данные и подмены внешних сервисов. Реальные CRM-записи и уведомления сотрудникам создавать только в разрешённом тестовом сценарии. Не запускать второй Telegram poller ради проверки.

## Публикация и сохранность данных

- Различать состояния: изменено локально, проверено, сохранено в Git, опубликовано и проверено на сервере. Сообщать «готово», когда выполнен согласованный объём, включая публикацию, если она входит в задачу. Ограничения и оставшуюся работу указывать прямо.
- Код бота версионировать в этом репозитории. Связанные мелкие правки можно объединять в один выпуск, сохраняя историю и возможность отката. Явный запрос немедленной публикации выполнять без искусственного ожидания других правок.
- Рабочие базы на VPS являются актуальным состоянием. Не заменять их локальными копиями при обновлении кода. Токены, webhook, регистрации и закрытые настройки не публиковать в Git и не выводить в журналы.
- Перед изменением работающего кода проверить текущую версию и требуемый способ отката; при работе с состоянием обеспечить подходящую резервную копию. Перезапускать только затронутые службы. Изменения документации и статических подписей сами по себе не требуют перезапуска бота.
- По завершении кратко сообщить, что изменилось, как проверено и где доступно. Не перечислять каждую техническую операцию. Существенные подтверждённые решения и выпуски добавлять в `EVOLUTION.md`; не объявлять локальный черновик опубликованным выпуском.
