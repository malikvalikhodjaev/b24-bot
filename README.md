## Подтверждённая задача

Пользователь выбрал @fom_bitrix_bot для менеджеров продаж Datfo Sales: открывать сделки, добавлять аптечные точки с привязкой распознанной по ИНН компании, подавать заявки в техническую поддержку, затем получать статистику.

Уточнение после чтения живой Б24: воронка 45 называется «Продажи и онбординг [KG]», 43 — «DATFO Новые продажи», 57 — «DATFO Развитие клиентов», 54 — «DATFO: работа с аптеками», 47 — «Техобслуживание [KG]». Прежнее название воронки 43 в локальных материалах больше не определяет её актуальное назначение. В текущем Sales-режиме новая продажа автоматически направляется в 45, в единственную рабочую стадию с названием «План»; разрешение подключения на запись проверяется самой Б24 при сохранении. Аптечный тип 1034, воронка 17, связь `companyId`, физический адрес, телефон и поле ответственного менеджера DATFO подтверждены REST-метаданными. Сделка связывается с аптекой через `parentId1034`. Смарт-процесс фармкомпаний 1130 не используется.

## Что реализовано

| Кнопка | Форма и результат |
|---|---|
| Открыть сделку | Сразу Mini App → новая аптека или существующая по FOM ID → необязательная заметка-напоминание с календарём и часом → просмотр → подтверждение → сделка в KG/План |
| Добавить аптеку в ОКБ | Форма новой аптеки: ИНН/компания, название, бизнес-регион и связанный город, адрес, текущая программа, необязательные контакт и геопозиция → просмотр → подтверждение |
| Заявка в поддержку | Mini App → новая аптека или FOM ID существующей → тема/описание → первый получатель и очередь → отправка → одна техзаявка в воронке 47, связанная с аптекой и компанией |
| Мои сделки и заявки в Б24 | Один список по 8 строк с перелистыванием → выбранная карточка → доступные действия. Стадии сделки меняются с отдельным подтверждением |
| Статистика | В рабочем Sales: два блока «Через бот» и «Всего в Б24» по дате создания карточки Б24. Сегодня, текущая неделя с понедельника, текущий месяц; «Мои» по текущему ответственному, «По команде» доступно администратору |

Поиск компании выполняется по точному `RQ_INN` в реквизитах компании Б24 (`ENTITY_TYPE_ID=4`). Даже единственное совпадение показывается менеджеру для подтверждения. Несколько совпадений требуют выбора. Перед новой записью принадлежность компании к ИНН перепроверяется. ИНН не является способом авторизации и не даёт доступа к чужим данным.

В форме новой аптеки ИНН обязателен. Если компании нет, менеджер вводит наименование; после итогового подтверждения создаются компания и её реквизиты по шаблону «Юр.лицо (UZ)». При нескольких совпадениях требуется выбор. Поиск в государственном реестре не подключён. Продажа и заявка для новой аптеки используют этот же механизм; для существующей компании используется текущая связь аптеки. Учебные формы сохраняются отдельно в `/test`.

Галочка «Создать этого человека на вас в Б24?» управляет контактом: без неё телефон сохраняется только в поле новой аптеки; с ней контакт находится или создаётся и связывается с компанией/аптекой. У найденного контакта сохраняются ФИО, телефоны и другие компании; новая связь не заменяет основную. Менеджер сохраняется в `assignedById` и в поле менеджеров DATFO. Новая аптека получает статус «Потенциальная» и стадию «Потенциальная аптека». Адрес фирмы не выводится из физического адреса аптеки. Выбор существующей аптеки по FOM ID не изменяет её справочные поля. Обмен УТ этой редакцией не менялся.

Сохранение состоит из отдельных устойчивых этапов: компания, реквизиты, контакт, связи, аптека и комментарий таймлайна. Потерянный ответ проверяется чтением; неподтверждённая запись не отправляется повторно. `/pending` проверяет результат, «Продолжить добавление в ОКБ» завершает оставшиеся подтверждённые шаги. Приём в УТ выполняется отдельно абонентским отделом. Точная карта полей и предложение для АРМ описаны в [OKB_UT_FIELDS.md](docs/OKB_UT_FIELDS.md); сама обработка УТ пока не изменена.

Разные точки одного юридического лица допускаются. Проверка существующей аптеки использует точное сочетание названия, адреса и ID компании в выбранном процессе/воронке. Это проверка точного совпадения, а не объединение похожих адресов или названий. Она выполняется только при подтверждённой компании.

### Пройти тестовую симуляцию в Telegram

Малик открывает [@fom_bitrix_bot](https://t.me/fom_bitrix_bot) и отправляет `/test` либо нажимает «🧪 Тестовая симуляция» в меню администратора. Доступ к этому режиму есть только у подтверждённого администратора; регистрация остальных менеджеров продолжает работать.

В симуляции используются те же формы сделки, аптеки, поддержки и статистики, но вымышленные компании и отдельная SQLite `data/simulation.sqlite3`. Реального REST-клиента Б24 в адаптере симуляции нет. Каждое сообщение формы помечено «ТЕСТ — Б24 не изменяется». Подтверждение создаёт учебный результат без ссылки на фиктивную CRM-карточку. Учебные операции не прибавляются к рабочей статистике. Состояние теста, черновики и учебные карточки переживают перезапуск.

Пример проверки аптечной точки:

3. Название аптеки: `Тестовая аптека`; телефон `90 123 45 67` → выбрать найденный учебный контакт.
4. Бизнес-регион: `Город Ташкент`; поиск района: `Мирабадский` → выбрать район.
5. Адрес: `Ташкент, учебная улица, 1` → «Без ориентира» → проверить данные → «Подтвердить».

Выход очищает только учебный черновик; регистрации и рабочие черновики сохраняются. Текущие журналы и PID записаны в `data/registration-process.json`; предыдущие журналы сохранены. После `/endtest` подтверждение формы ОКБ уже обращается к реальной Б24.

Требования: Python 3.11+, SQLite из стандартной библиотеки и доступная база часовых поясов для `Asia/Tashkent`. В проверенной рабочей среде Codex всё это уже доступно.

Метаданные сделок/аптек доступны; живая попытка добавления в воронке 43 отклонена `ACCESS_DENIED`, запись отсутствует. Отдельная роль для этого подключения подготовлена и ожидает разрешения пользователя.
3. Скопировать `settings.example.json` в `settings.json` и указать администратора: Telegram `855438267`, Б24 `132`, имя «Малик Валиходжаев», `admin: true`. При наличии `registration.json` остальные менеджеры подключаются через регистрацию и подтверждение; их числовые ID вручную собирать не требуется. Доступ определяется актуальными подтверждёнными привязками SQLite; старый статический список не заменяет подтверждение. Без режима регистрации используется только явный список `settings.users`.
4. В текущем `--sales-bot` продажа закреплена за воронкой 45. Стадия «План» определяется по актуальному имени из Б24; если она отсутствует или неоднозначна, запись блокируется. Старые неподтверждённые формы предлагают начать новую, прежний черновик остаётся в журнале. Настройки примера для запуска без регистрации не заменяют рабочий маршрут.
5. Карта аптечного процесса уже заполнена подтверждёнными полями в `settings.example.json`: нужны `title`, `company_id`, `responsible_id`, `request_id`, `address` и `phone`. `manager_ids` дополнительно связывает менеджера с профильным полем DATFO. Отсутствующее описание сохраняется в таймлайне. Любой введённый ИНН сохраняется вместе с исходными данными формы.
6. В текущем Sales-режиме поддержка создаётся сделкой выбранной в форме воронки, ответственный — зарегистрированный менеджер. Назначение техническому специалисту, рабочий коммуникационный инбокс и адаптер задач/смарт-процесса этой редакцией не подключены. Прежний запуск без регистрации допускает отдельную настроенную цель `support` и фиксированного ответственного; эти настройки не подменяют форму Sales.
7. Выполнить локальную и сетевую проверки, затем запустить приложение:

```powershell
.\Start-Bot.ps1 -Check
.\Start-Bot.ps1 -CheckOnline
.\Start-Bot.ps1
```

`--check` проверяет формат локальных настроек. `--check-online` подтверждает имя бота через `getMe`, отсутствие существующего webhook, реальные записываемые поля и выбранные воронки Б24; выполняет только чтение. Он не доказывает наличие права добавления карточек: это подтверждается первым рабочим сохранением. Настройки полей перепроверяются перед каждой записью, поскольку Б24 может молча проигнорировать неизвестное поле.

Для пользовательских полей применяется `useOriginalUfNames=Y`: в карте нужны точные имена из `crm.item.fields` с этим параметром. Внешний номер запроса — `originId` для сделки и обычно `xmlId` для смарт-процесса. Все указанные поля проверяются по метаданным, включая поле связи с компанией. Несуществующие поля не заменяются догадками. Переменные `.env` не переопределяют уже заданные переменные процесса.

### Получить Telegram ID перед настройкой доступа

Открыть [@fom_bitrix_bot](https://t.me/fom_bitrix_bot), нажать Start или отправить `/whoami`. Бот вернёт числовой ID. Сопоставление с учётной записью Б24 и ролью руководителя выполняется отдельно; получение ID само по себе не даёт прав. Этот режим можно запустить командой:

Режим получения ID остановлен при включении регистрации. Старый файл `data/identify.pid` — историческая запись; перед любым завершением процесса требуется проверить реальную команду и путь исполняемого файла. Один бот не должен иметь два одновременно работающих poller-процесса.

1. Менеджер открывает [@fom_bitrix_bot](https://t.me/fom_bitrix_bot), нажимает Start и вводит имя и фамилию, как в Б24.
2. Бот ищет активного внутреннего сотрудника и предлагает выбрать свою учётную запись. Ни имя, ни наличие Telegram username сами по себе не выдают доступ.
3. Малик открывает «Заявки менеджеров» (`/registrations`), проверяет, что это нужный менеджер Datfo Sales, и нажимает «Подтвердить …». Принадлежность к Sales сейчас проверяет Малик: организационный отдел автоматически не определяется.
4. Менеджер проверяет подтверждение через «Моя регистрация» (`/profile`) или `/start`. Статус не рассылается автоматически при подтверждении.

`/members` показывает подключённых сотрудников. Кнопки отклонения и отключения доступны только администратору. Одна учётная запись Б24 может иметь одну подтверждённую привязку Telegram. Отключение сразу убирает адресата из маршрутизации, закрывает доступ к формам и прежним сохранённым ответам, очищает черновик. Отклонённую заявку можно подать заново; отключённая привязка требует ручного решения администратора. Изменение администраторов в JSON применяется после перезапуска.

Числовой Telegram ID и ID личного чата сохраняются автоматически. Username необязателен и не является ключом привязки; телефон и пароль Б24 не запрашиваются. `Store.recipient(bitrix_id)` возвращает единственный подтверждённый личный чат для будущих уведомлений по ответственному Б24. Наблюдение за событиями Б24, рассылки и отчёты по расписанию пока не подключены. Бот может писать в личный чат только после первого обращения пользователя; эти правила описаны в [Telegram Bot API](https://core.telegram.org/bots/api#user) и [введении Telegram](https://core.telegram.org/bots#how-are-bots-different-from-humans).

Запуск и проверка:

```powershell
.\Start-Bot.ps1 -RegistrationOnly -CheckOnline
.\Start-Bot.ps1 -RegistrationOnly
```

Рабочий режим регистрации и ОКБ:

```powershell
.\Start-Bot.ps1 -SalesBot -CheckOnline
.\Start-Bot.ps1 -SalesBot
```

`-SalesBot -CheckOnline` проверяет метаданные чтением. `-SalesBot` включает ОКБ для подтверждённых менеджеров. `-RegistrationOnly` сохраняет прежний режим без рабочих записей CRM. Сейчас работает один скрытый процесс `--sales-bot`; не запускайте второй poller того же бота. Бот работает, пока включён этот компьютер; размещение на VPS не выполнено.

`-RegistrationOnly -CheckOnline` выполняет только чтение Telegram и Б24. PID действующего режима записан в `data/registration.pid`, режим и актуальные пути журналов — в `data/registration-process.json`. Исторические журналы сохранены. Перед сменой режима проверяется команда, исполняемый файл и время создания именно этого процесса; регистрации остаются в той же SQLite. VPS и другие службы этой задачей не менялись.

## Надёжность и границы

- Черновики, результаты и смещение Telegram сохраняются в локальной SQLite. Переигрывание того же входящего сообщения повторяет ответ, но не продвигает форму и не создаёт новую запись.
- Перед отправкой записи сохраняется её номер. Если ответ потерян или процесс прервался после отправки, `/pending` только ищет карточку по этому номеру. Если Б24 пока не подтвердил результат, повторная запись блокируется до проверки администратором. Отмена формы такую неопределённость не снимает.
- Блокировка базы допускает один процесс приложения. Другие интеграции Б24 могут создавать карточки независимо; глобальная уникальность адресов аптек не гарантируется.
- Работа ведётся в личном чате. Доступ задаётся подтверждённой привязкой регистрации либо явным списком Telegram ID в режиме без регистрации; отключение и снятие роли руководителя запрещают также повторную выдачу сохранённых ответов с прежними правами. `/whoami` показывает только ID обратившегося пользователя.
- Рабочий Sales /stats читает счётчики Б24: «Через бот» по origin/XML_ID этого бота, «Всего в Б24» без ограничения источника. Оба блока считают сохранённые карточки по native-дате создания; удалённые записи не входят. «Мои» — текущий ответственный, «По команде» — все доступные подключению записи. Офлайн-симуляция сохраняет прежний журнал подтверждённых созданий по времени подтверждения. Найденная существующая аптека не получает метку нового создания.
- Полная статистика Sales, звонки, стадии, планы и финансовые показатели пока не подключены. Для следующей итерации нужно выбрать конкретные показатели существующего Datfo Sales и их периоды.
- Геопозиция аптеки необязательна: Telegram или форма передают широту/долготу в поля Б24. Фото, файлы и общее редактирование карточек пока не включены; поддержка синхронизирует стадии по отдельному маршруту.
- Промышленное развёртывание, автоматический перезапуск и резервное копирование базы пока не настроены. Сырые файлы, CRM-схема и рабочие службы текущей задачей не изменялись.
